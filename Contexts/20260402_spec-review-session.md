## 3. 重要な決定（Key decisions）

- 結論: 背景・課題と利用シーン・要求を分離した。
  - 理由: `問題` と `使われる条件` と `実装要件` が混在しており、仕様判断の軸が曖昧だったため。
  - 記録先: `docs/ai-news-agent-spec.md` の `1. 概要`

- 結論: MVP は `読む用途` を主軸にする。
  - 理由: 中核価値は `複数ソース横断 / 重要度順 / 完全翻訳 / 2〜3分` であり、Markdown 出力だけで先に検証できるため。
  - 記録先: `docs/ai-news-agent-spec.md` の `利用シーン・要求`、`開発方針`、`Phase 1`

- 結論: 音声は MVP では `簡易版` を任意生成し、品質向上は後続フェーズに回す。
  - 理由: 音声品質まで同時に詰めると MVP の論点が増え、読む用途の成立を遅らせるため。
  - 記録先: `docs/ai-news-agent-spec.md` の `音声ダイジェスト仕様`、`Phase 4`、`成功基準`

- 結論: TUI での音声生成既定値は `No` に変更した。
  - 理由: MVP は読む用途優先であり、音声は補助機能として扱う方針と整合させるため。
  - 記録先: `docs/ai-news-agent-spec.md` の `5. TUI 対話フェーズ設計`

## 9. リスク（Risks / gotchas）

- 音声を MVP に残しすぎると Phase 1 のスコープが膨らむ。
  - 回避策: `簡易版・任意生成・既定OFF` を維持する。

  - 回避策: MVP ではソースを最小化し、Phase 2 以降で拡張する。

  - 回避策: 対象範囲と NG パターンを具体的に決める。
