### source adapter と official_blog_worker

- source adapter は source 固有の取得、抽出、最低限の正規化まで担当することに決定した。
- `official_blog_worker` は複数 adapter の並列実行、`SourceRunResult[]` への集約、失敗整理に限定することに決定した。
- 後から source を追加する場合は、adapter を追加して `official_blog_worker` の adapter 一覧へ登録する方針にした。

### contentRef と本文保存

- `contentRef` は記事本文そのものではなく、本文を置いてある場所を指す参照パスだと整理した。
- MVP-0 では記事本文をローカル Markdown ファイルとして保存し、`CandidateItem` には `contentRef` だけを入れることに決定した。
- DB 保存は hosted DB が MVP-0 scope 外であり、schema / migration / 接続 / 永続化エラー処理が重いため後回しにした。

### Markdown 出力先

- 記事本文は `output/content/{runId}/{candidateId}.md` に保存することに決定した。
- 最終 research brief は `output/briefs/{runId}/ai-research-brief.md` に保存することに決定した。
- `runId` 単位にすることで、同じ日に複数回実行しても上書きされず、中間本文と最終 brief を対応付けられる。

### 実装技術

- 当初は素の TypeScript + Node.js を提案したが、保守性の観点から最初から LangGraph.js を使う案を再検討した。
- 最終的に、MVP-0 は TypeScript + Node.js + LangGraph.js で実装する方針に決定した。
- LangGraph.js は orchestration に限定し、source adapter / translation / output などの business logic は通常 module として分離する。
- MCP server は外部 interface であり、MVP-0 の中核検証には直接効きにくいため後回しにした。

## Decisions（決めたこと）

- source adapter は source 固有の取得・抽出・最低限の正規化まで担当する。
- `official_blog_worker` は adapter の実行と `SourceRunResult[]` 集約に限定する。
- `contentRef` はローカル Markdown 本文ファイルへの参照パスにする。
- MVP-0 では DB 保存をしない。
- 記事本文は `output/content/{runId}/{candidateId}.md` に保存する。
- 最終 research brief は `output/briefs/{runId}/ai-research-brief.md` に保存する。
- MVP-0 は TypeScript + Node.js + LangGraph.js で実装する。
- LangGraph.js は orchestration に限定し、business logic は通常 module に分離する。
- MCP server は MVP-0 では後回しにする。

## Notes（メモ / 学び）

- LangGraph.js はコード量を直接大きく減らすというより、workflow と shared state の境界を framework に乗せて保守しやすくする効果が大きい。
- `contentRef` を導入すると、manager 用 metadata と translation / output 用本文を分離しやすい。
- 実装詳細設計は1つの決定ログに追記する運用にすると、後から判断経緯を追いやすい。
