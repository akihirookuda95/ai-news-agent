## 1. 概要

### 背景・課題

AI 技術の進化が速く、毎日大量のニュースが世界中で発信されている。一方で、現在の情報収集には次の課題がある。

- **情報源の偏り**  
  普段の情報収集は X のタイムラインへの依存度が高い。しかしタイムラインには「自分がフォローしている人」のポストが中心に流れるため、情報源が自分の所属コミュニティや関心領域に強く偏る。未フォローの人や媒体にも重要な一次情報や異なる観点が含まれていても、現状の導線では拾いにくい。

- **情報量の多さによる取りこぼし**  
  タイムライン型のメディアでは情報が次々に流れていくため、すべてを読むことは現実的ではない。本当に重要な情報と、今すぐ追わなくてよい情報を切り分け、優先度の高いものから短時間で把握できる状態が必要である。

- **現行ワークフローの品質不足と速度不足**  
  会社 PC では Codex の Skills を使い、Hacker News・dev.to・Reddit を検索ソースとしてテックニュースを取得し、Markdown に出力している。しかし翻訳結果が完全翻訳ではなく要約になってしまうケースがあり、原文と同等の情報量を日本語で読みたいという要求を満たせていない。さらに処理完了まで **約 10 分**かかることがあり、日常的な情報収集フローとしては遅い。

### ターゲットユーザー

本プロダクトの一次ターゲットユーザーは、**英語圏のAI一次情報を追いたい日本語圏のAIエンジニア / ソフトウェアエンジニア / 個人開発者**である。

このユーザーは、AI・LLM・エージェント・検索・開発ツール周辺の変化を継続的に追う必要がある一方で、日々の業務や開発の中で情報収集に長時間を割くことは難しい。普段は X、Hacker News、Reddit、GitHub、公式ブログなどを断続的に見ているが、情報源がフォロー関係や日々の偶然に左右されやすく、重要な一次情報を安定して拾えている感覚がない。

また、このユーザーは英語の技術記事を読むこと自体は可能でも、毎日フルで読むのは負荷が高いと感じている。そのため、日本語で素早く内容を把握したい一方で、モデル名、API 名、SDK 名、コード、技術用語などは原文のまま保持されることを望む。単なるニュース要約ではなく、**今日どの情報を読むべきか、何が新しく、誰に関係があり、試す価値があるのか**を短時間で判断したい。

さらにこのユーザーは、情報収集の目的が教養的なニュース消費ではなく、**実装判断・技術選定・学習優先度の決定**に近い。日常的に CLI やエディタを使うため、ニュース収集も既存の作業導線の中で扱えることを好む。`ai-news-agent` は、このようなユーザーに対して、英語圏のAI一次情報を技術語を壊さず日本語で整理し、重要な変化を短時間で判断しやすくする実務ブリーフィングを提供することを目指す。

価値提案としては、`ai-news-agent` は、**英語圏のAI一次情報を、技術語を壊さず日本語で整理し、AI実務者が重要な変化を短時間で判断しやすくすること**を目指す。

### ターゲットユーザーの日次行動

一次ターゲットユーザーは、平日の午後など仕事で疲れたタイミングに、短時間で情報収集することが多い。主な導線は X であり、まずタイムラインを見て、気になった投稿があればその先のページへ遷移する。X から大きく離れずに情報を眺めることが多く、Zenn は日本語圏の技術トレンドをざっと確認する用途で使われる。

情報収集に使う時間は 1 日あたり 15 分〜1 時間程度で、その日の余裕や疲労度に左右される。気になった情報は X のブックマークやリンク保存で後回しにし、時間に余裕があるときにまとめて見返す。情報収集の目的は単なるニュース消費ではなく、仕事や個人開発に役立つ変化を見つけ、実装や技術選定に活かすことである。

### ターゲットユーザーの主要な詰まりポイント

- **X 依存による情報源の偏り**  
  情報収集の起点が X に強く依存しているため、フォロー関係やおすすめアルゴリズムに左右されやすい。特に欧米圏の一次情報や、フォロー外の技術トレンドへの到達が不安定になりやすい。

- **英語圏の一次情報・議論を追う負荷**  
  短いリリース告知は英語のまま読めても、公式ドキュメント、Reddit の議論、GitHub Issue / PR の議論のような長文・細かい条件・背景理解を要する内容は負荷が高い。その結果、本来追いたい情報に十分ついていけない。

- **翻訳の手間と品質への不満**  
  ChatGPT 等で都度翻訳すること自体が手間であり、時間の無駄や面倒さを感じやすい。また、既存の Skills ベースのフローでは完全翻訳ではなく要約寄りの出力になることがあり、原文と同等の情報量を得たい要求を満たせていない。

- **速度不足による継続利用の阻害**  
  現在のニュース取得フローは完了までに時間がかかり、せっかちな利用者にとっては待ち時間が大きなストレスになる。品質が高くても遅いと日常的には使われにくい。

- **後で読む情報の蓄積**  
  気になった情報を保存しても、見返すのは時間に余裕があるときに限られるため、一定量が未消化のまま蓄積しやすい。

### MVP が優先して解く課題

MVP では、次の課題を優先的に解く。

1. 英語圏の AI 一次情報や関連議論を、高品質な日本語で短時間に理解しやすくすること
2. X のタイムラインに依存しない複数ソース導線を作り、情報源の偏りを下げること
3. 待ち時間を短くし、日常的に使える速度で結果を返すこと
4. 保存して後回しにしなくても、その場で重要な変化を把握しやすくすること

### 利用シーン・要求

本プロダクトは、日常的な情報収集フローの中で無理なく使い続けられることを重視する。現時点で想定している主な利用シーンと要求は次のとおり。

現時点の開発方針として、**MVP は「読む用途」を主軸**とする。Markdown による読書体験、完全翻訳、重要度順の整理、実行速度の改善を先に成立させる。**「聞く用途」は次フェーズで強化する**前提とし、MVP では補助的な価値として扱う。

- **読む用途への最適化**  
  作業前後や短い空き時間に、重要度順に整理されたニュースを Markdown で素早く確認できること。

- **聞く用途への最適化**  
  平日の昼休みには脳を回復させるためにウオーキングする習慣がある。毎日ではなくても、疲れていない日は歩きながら iPhone で情報を聞いてキャッチアップしたい。そのため、テキスト出力だけでなく音声でも消費できること。なお、MVP の音声は簡易版に留め、品質向上は後続フェーズで行う。

- **普段の作業導線に組み込めること**  
  仕事・私用の両方で Codex CLI を日常的に使っているため、ai-news-agent も Codex CLI から直接呼び出せること。

- **短時間で結果が得られること**  
  情報収集の開始から結果取得までが長すぎると継続利用しにくいため、1 回の実行は **2〜3 分程度**で完了することを目標とする。

### このエージェントが解決すること

- X のフォロー関係に依存しない複数ソースから AI 関連ニュースを収集し、情報源の偏りを下げる
- 大量の候補記事を重要度順に整理し、短時間で追うべき情報だけを優先表示する
- 英語記事を**原文構造を保った完全な日本語翻訳**で提供する（技術用語・コード・プロダクト名は英語のまま保持）
- 重複記事を除去し、限られた時間でも情報密度高く読めるようにする
- 結果を Markdown ファイルにまとめ、短時間で読める形に整形する
- 音声ダイジェストを生成し、読む時間が取りにくい場面でもキャッチアップできるようにする

### 概要レベルの成功条件

- 情報源の偏りを下げるため、単一の SNS タイムラインではなく複数ソースを横断して収集できること
- 取りこぼしを減らすため、重要度順に並べ替えられた結果を短時間で確認できること
- 翻訳品質の課題を解消するため、要約ではなく完全翻訳を安定して提供できること
- 日常利用に耐えるため、Codex CLI から呼び出せて **2〜3 分程度**で結果を返せること
- MVP では Markdown 出力の品質を主軸に成立させ、音声出力は簡易版を任意で提供できること

### ゴール（最終形）

Claude Code / Codex CLI の TUI 上で対話的に情報ニーズを明確にし、その結果を元に ai-news-agent が内部でエージェンティックに情報収集・評価・翻訳・整形を実行し、**2〜3 分程度でダイジェスト md を生成する。音声ダイジェストは必要に応じて生成でき、品質向上は後続フェーズで進める**。

**例**:
```
> 今日はどんな情報が欲しいですか？
→ Hacker News で今盛り上がっている AI 関連のニュース、ここ 1 週間分

> 取得件数は？（デフォルト: 10 件）
→ 5 件でいい、今日は忙しいから

→ [ai-news-agent 起動 → Hacker News から情報収集 → 完全翻訳 → md 生成（必要に応じて簡易音声生成）]
```

```
> 今日はどんな情報が欲しいですか？
→ 仕事に直結するライブラリの更新情報が欲しい

> 最近使っているライブラリを教えてください
→ LangGraph, Cohere, Elasticsearch

> 更新情報のみ、それとも使い方の記事も？
→ 更新情報のみ

→ [ai-news-agent 起動 → 公式 docs・GitHub Releases から情報収集 → 完全翻訳 → md 生成（必要に応じて簡易音声生成）]
```

## 3. 情報ソース設計

### MVP で優先する情報源

MVP では、**LLM アプリケーション実務に直結する一次情報を狭く深く追う**ことを優先する。広く集めすぎると速度と品質が落ちるため、Phase 1 では対象領域と情報源を意図的に絞る。

#### MVP の主な追跡対象

- OpenAI
- Anthropic
- LangChain
- LangGraph
- LlamaIndex
- Cohere
- Chroma
- Elasticsearch

#### MVP の優先取得元

- **公式ブログ / 公式発表**
  - OpenAI, Anthropic, LangChain, Cohere, Chroma, LlamaIndex など
- **GitHub Releases / Changelog**
  - LangChain, LangGraph, LlamaIndex, Chroma, Codex CLI, Elasticsearch など
- **公式ドキュメント更新**
  - breaking change や新機能把握に必要な範囲
- **Hacker News**
  - 上記一次情報がどの程度話題化しているかを補助的に確認する

Hacker News は一次情報そのものではないが、**ノイズが比較的少なく、開発者にとって重要な話題が上がりやすい**ため、MVP でも補助ソースとして残す。

#### MVP では主導線にしない情報源

- X
- Reddit
- dev.to
- Zenn
- Qiita
- 一般ニュースメディア

これらは将来フェーズで拡張候補とする。特に Reddit は情報量が多い一方でノイズも多いため、導入時は `r/LangChain` のような **仕事で使っている技術に直結するサブレディットだけを選定して追加する**。MVP では、**公式情報中心** に寄せることで、ターゲットユーザーの主要課題である「英語圏の一次情報を追いたい」「速度と品質の両方がほしい」に集中する。

### 固定ソース

| コミュニティ | Hacker News | AI 関連のトレンド記事 |

### 情報抽象度レイヤー

ユーザーがその日知りたい情報の「粒度」によって、参照するソースと収集戦略が変わる。

## 4. フォールバック付き多段フェッチ戦略

固定ソースから取得した情報が「量・質」の基準を満たさない場合、追加ソースへ段階的にフォールバックする。これにより毎日・毎週、安定した量と品質のダイジェストを生成できる。Phase 1 の MVP では、まず **公式ブログ / GitHub Releases / 公式ドキュメント / Hacker News** を固定ソースとして扱う。

```
[Step 1] 固定ソース取得（公式ブログ, GitHub Releases, 公式ドキュメント, Hacker News）
         ↓
         品質・量チェック（LLM-as-judge）
         ┌─ 十分 → [Step 5] へ
         └─ 不足 ↓

[Step 2] 抽象度レイヤーに対応する追加ソース取得（Web 検索など）
         ↓
         品質・量チェック
         ┌─ 十分 → [Step 5] へ
         └─ 不足 ↓

[Step 3] さらに広範なソースを追加（Multi-Query 展開）
         ↓
         品質・量チェック
         ┌─ 十分 → [Step 5] へ
         └─ n 段階まで繰り返し

[Step 5] 最終フィルタリング・整形 → md 生成（必要に応じて簡易音声生成）
```

**品質・量の判断基準（内側エージェントが担当）**:
- 記事数が `limit` に対して著しく不足していないか
- スコアリングで「高・中」評価の記事が一定数あるか
- ソースの多様性（同一サイトに偏っていないか）

## 5. TUI 対話フェーズ設計

実行前に Claude Code / Codex CLI（外側エージェント）がユーザーと対話し、情報ニーズを明確にする。

MVP では、対話は**必要最小限**に絞る。基本は `自由入力 + 件数 + 音声有無` の 3 点で開始し、対象ライブラリや媒体などの追加質問は **必要な場合のみ** 行う。

### 対話の流れ

```
今日はどんな情報が欲しいですか？
  → [自由入力]
  例: "Hacker News で今盛り上がっている AI 関連のニュース、ここ 1 週間分"
  例: "今日のトレンドニュースを 10 本"
  例: "仕事に直結するライブラリの更新情報"

（必要な場合のみ追加質問）
例:
  ・「仕事直結」と入力した場合 → 使用ライブラリ・フレームワークを確認
  ・「世界の流れ」と入力した場合 → 特定トピックに絞るか確認
  ・「新ツール」と入力した場合 → 言語・領域の絞り込みを確認
  ・媒体指定あり → そのまま採用、追加質問は最小限

取得件数の目安は？（デフォルト: 10 件）
  → [入力またはスキップ]
  ※ ユーザーの気分や忙しさに応じて柔軟に変更可能（3〜20 件程度）

音声ダイジェストも生成しますか？（デフォルト: No）
  → [Yes / No]

確認: [要約された情報ニーズ]でよいですか？
  → [Yes / 修正]
```

**MVP の標準質問**:

1. 何の情報が欲しいか（自由入力）
2. 取得件数は何件か（デフォルト 10 件）
3. 音声ダイジェストも生成するか（デフォルト No）

対象ライブラリ、特定媒体、日付範囲などは、入力内容だけでは判断が難しい場合に限って追加で確認する。

### 対話結果の渡し方

対話で得た情報を構造化して内側エージェントに渡す：

```typescript
interface NewsRequest {
  query: string;           // 例: "LangGraph Cohere Elasticsearch 更新情報"
  abstractionLayer: "macro" | "middle" | "micro";
  targetSources?: string[];// 例: ["github_releases", "official_docs"]
  date: string;            // 例: "today" | "past_week"
  limit: number;           // 例: 10（3〜20 の範囲で柔軟に指定可能）
  userIntent: string;      // 対話の要約（LLM 用コンテキスト）
  generateAudio: boolean;  // 音声ダイジェスト生成の有無
}
```

## 6. 翻訳仕様

### 基本方針

**要約ではなく完全翻訳**を行う。ユーザーが原文を読むのと同等の情報量を日本語で得られることを目指す。

ただし、MVP における完全翻訳の対象範囲は **本文中心** とする。記事本文・見出し・箇条書きは翻訳対象に含めるが、**表は翻訳対象外** とする。GitHub Issue / PR、Reddit などの議論系ソースを将来扱う場合に、どこまでを翻訳対象にするかは別途検討する。

### ルール

| 項目 | 方針 |
|---|---|
| 技術用語 | 英語のまま保持（例: embedding, fine-tuning, RAG, MCP） |
| 固有名詞 | 英語のまま保持（例: LangGraph, Hacker News） |
| 文章構造 | 原文の段落構造・見出し構造を維持 |
| コードブロック | そのまま保持（翻訳しない） |
| 翻訳対象 | 本文、見出し、箇条書き（掻い摘んだ要約は行わない） |
| 翻訳対象外 | 表、コードブロック |
| 文体 | 自然な日本語（直訳調にならないよう注意） |

### NG パターン

- ❌ 原文を要約して翻訳する
- ❌ 「この記事では〜について述べています」のようなメタ的要約
- ❌ 技術用語を無理に日本語化する（例: ❌「埋め込み」→ ✅「embedding」）
- ❌ 表の内容を無理に日本語へ変換してレイアウトを崩す

## 7. 音声ダイジェスト仕様

### 概要

収集した記事群の**要約ダイジェスト音声**を音声ファイルとして生成する。朝の準備中や散歩中にハンズフリーで情報をキャッチアップすることが目的である。

ただし、**MVP の主軸は Markdown による読書体験**であり、音声は補助機能として扱う。MVP 段階では「聞けること」を優先し、話し方・構成・自然さ・聞きやすさの品質向上は後続フェーズで行う。

### 仕様

| 項目 | 内容 |
|---|---|
| 形式 | MP3 または WAV |
| 長さ | 3〜10 分（記事数に応じて可変） |
| 言語 | 日本語 |
| MVP スタイル | 記事ごとの要約読み上げを中心とした簡易ダイジェスト |
| 将来スタイル | ポッドキャスト風ダイジェスト（導入・つなぎ・締めを含む自然な構成） |
| MVP 構成 | 記事タイトル → 各記事の概要（重要度順） |
| 将来構成 | イントロ → 各記事の概要（重要度順）→ クロージング |

### 音声生成の流れ

```
[1] 翻訳済み記事群から音声用スクリプトを生成（LLM）
    - MVP: 各記事を 20〜40 秒程度の日本語要約に変換
    - 将来: 自然な接続詞や導入文を追加して聞きやすさを改善

[2] TTS API で音声ファイルを生成
    - 候補: OpenAI TTS / ElevenLabs / Google Cloud TTS

[3] 出力
    - md ファイルと同じディレクトリに音声ファイルを配置
    - md 内にリンクを記載
```

### md との違い

| | md（完全翻訳） | 音声（ダイジェスト） |
|---|---|---|
| 情報量 | 原文と同等 | 要約（概要レベル） |
| 用途 | じっくり読む | ながら聞き |
| 生成コスト | 翻訳のみ | 翻訳 + スクリプト生成 + TTS |
| MVP での優先度 | 主軸 | 補助機能 |

## 8. パフォーマンス目標

### 現状と目標

| 指標 | 現状（Skills ベース） | 目標 |
|---|---|---|
| 5 記事の取得〜md 生成 | - | **2 分以内** |
| 10 記事の取得〜md 生成 | 約 10 分 | **3 分以内** |
| 翻訳品質 | 要約ベース（情報欠落あり） | 完全翻訳 |
| 音声品質 | 未整備 | MVP は簡易版、品質向上は後続フェーズ |

### 測定条件

MVP のパフォーマンス目標は、次の条件で測定する。

- 測定範囲は、**コマンド実行開始から Markdown 生成完了まで**
- **キャッシュなし** の初回実行を基準とする
- **音声生成なし** を基準とする
- 対象ソースは、Phase 1 の MVP ソースである **公式ブログ / GitHub Releases / 公式ドキュメント / Hacker News** とする
- 記事取得、重要度判定、翻訳、Markdown 書き出しを含む

音声生成時間は MVP の主要性能指標には含めず、将来フェーズで別途管理する。

### 高速化の方針

- **記事取得の並列化**: 複数ソースへの fetch を `Promise.all` / `Promise.allSettled` で並列実行
- **翻訳の並列化**: 記事ごとの翻訳を並列実行（API rate limit に注意）
- **不要な再取得の回避**: キャッシュ層の導入（同日中の同一 URL はスキップ）
- **ストリーミング出力**: 翻訳完了した記事から順次 md に書き出し（全記事完了を待たない）

## 9. アーキテクチャ概要

### 全体構造の考え方

最終形の `ai-news-agent` は、単一の LLM 呼び出しで完結するニュース取得ツールではなく、**manager 主導の階層型マルチエージェント**として構成する。1 つの manager agent が全体方針、探索ラウンド、停止条件、最終出力を管理し、複数の worker agent が担当領域ごとに情報収集・評価・翻訳を実行する。

この構造を採る理由は、情報源の種類が複数あり、かつ「まだ取り切れていない情報を追加で探す」「収集結果を見て探索方針を修正する」「翻訳品質を別工程で確認する」といった段階的な判断が必要だからである。

### 全体構造：二重エージェント（Mixture of Agents）

```
┌─────────────────────────────────────────────────────┐
│  外側エージェント：Claude Code / Codex CLI（TUI）     │
│                                                     │
│  ① ユーザーと対話し情報ニーズを明確化                 │
│  ② NewsRequest を構築し fetch_ai_news を呼び出す      │
│  ③ 結果の md を表示し、必要に応じて音声ファイルのパスを案内│
└───────────────────┬─────────────────────────────────┘
                    │ MCP tool call（NewsRequest）
                    ↓
┌─────────────────────────────────────────────────────┐
│  内側エージェント：ai-news-agent（MCP サーバー）       │
│                                                     │
│  ニュース収集に特化したエージェントループを実行         │
│  LLM（プランナー）が以下のツールを自律的に呼び出す      │
│                                                     │
│    ├─ fetchRSS        RSS フィードから記事取得         │
│    ├─ webSearch       Web 検索で最新情報を補完         │
│    ├─ fetchTechBlog   テックブログから記事取得          │
│    ├─ checkDuplicate  embedding による重複判定         │
│    ├─ scoreArticle    LLM-as-judge で重要度評価       │
│    │                  ＋ フォールバック判断            │
│    ├─ translateFull   英語 → 日本語 完全翻訳           │
│    ├─ generateScript  簡易音声用スクリプト生成          │
│    ├─ generateAudio   TTS による音声ファイル生成        │
│    └─ writeMarkdown   md ファイル出力                 │
│                                                     │
│  品質・量が基準を満たすまでフォールバックループを実行   │
│  十分な情報が集まったと判断したら md を返し、必要時のみ音声も返す│
└─────────────────────────────────────────────────────┘
```

### エージェントの役割

#### 1. Manager / Planner Agent

manager agent は、ユーザー要求と収集状況を見ながら、全体の処理方針を決定する責務を持つ。

主な役割:

- 初期の探索計画を立てる
- worker に担当ソースや担当トピックを割り振る
- 各 worker から共有された候補情報を見て、情報量・偏り・一次情報の不足を判断する
- 不足している情報があれば再探索を指示する
- 収集完了後に翻訳対象を確定する
- 最終的な重要度順、出力内容、返却形式を決定する

#### 2. Source Worker Agents

source worker agent は、担当ソースまたは担当クエリに基づいて情報収集を行う。

想定例:

- 公式ブログ担当
- GitHub Releases / Changelog 担当
- Hacker News 担当
- 対象ライブラリ・対象企業の公式 docs 担当

主な役割:

- 担当ソースから候補記事・更新情報を取得する
- 候補ごとに基本メタデータを抽出する
- 一次情報かどうか、対象技術との関連度が高いかを付与する
- 取得結果を共有メモリに登録する

#### 3. Judge / Dedupe Agent

judge / dedupe agent は、収集された候補群を評価し、重複除去と重要度の初期判定を行う。

主な役割:

- 同一トピックや同一更新を重複判定する
- 一次情報を優先し、二次情報や周辺情報を補助扱いにする
- 重要度の初期ラベルを付与する
- manager に対して「まだ情報が不足しているか」を判断材料として返す

#### 4. Translation Agent

translation agent は、収集完了後に対象記事を完全翻訳する。

主な役割:

- 本文、見出し、箇条書きを日本語へ翻訳する
- 技術用語、API 名、SDK 名、コード、固有名詞を保持する
- 原文構造を維持したまま、要約化せずに翻訳する

#### 5. Translation QA Agent

translation QA agent は、翻訳品質を点検する。

主な役割:

- 要約化されていないかを確認する
- 技術用語が壊れていないかを確認する
- 段落構造が維持されているかを確認する
- 不自然な誤訳や意味欠落があれば再翻訳対象として差し戻す

### 共有メモリの方針

各エージェントは記事全文を相互に渡すのではなく、まず **構造化された共有メモリ** を介して情報を共有する。これはコンテキスト肥大化を防ぎ、manager が全体状況を判断しやすくするためである。

共有メモリに保持する最低限の項目例:

- `id`
- `title`
- `url`
- `sourceType`
- `sourceName`
- `publishedAt`
- `isPrimarySource`
- `topicTags`
- `shortSummary`
- `relevanceScore`
- `status`

### 処理の流れ

1. manager agent がユーザー要求を受け取り、初期探索方針を作る
2. source worker agents が担当ソースごとに候補を収集する
3. judge / dedupe agent が候補群を評価し、重複除去と重要度の初期判定を行う
4. manager agent が情報量・偏り・一次情報不足を見て、必要なら追加探索を指示する
5. 収集条件を満たしたら、manager agent が翻訳対象を確定する
6. translation agent が完全翻訳を行う
7. translation QA agent が翻訳品質を確認し、必要なら再翻訳を返す
8. manager agent が最終的な並び順と出力内容を確定し、Markdown と必要に応じて音声生成へ渡す

### 設計上の注意

- Phase 1 ではこの構造をそのまま実装せず、固定パイプラインで代替する
- Phase 2 以降で、manager + source worker + judge の構成から段階的に導入する
- エージェント数を増やしすぎると速度が悪化するため、初期は最小構成に留める
- 翻訳 QA は品質向上に有効だが、性能目標とのバランスを見ながら導入する
- Reddit や議論系ソースを扱う場合は、共有メモリと重複判定の粒度をより厳密に設計する必要がある

### 内側エージェントの処理フロー

```
[1] リクエスト受信
    外側から NewsRequest（query / abstractionLayer / limit 等）を受け取る

        ↓

[2] ソース選択
    abstractionLayer に基づき固定ソース群を決定

        ↓

[3] 情報収集（フォールバックループ）【並列実行】
    fetchRSS / webSearch / fetchTechBlog を並列実行
    → scoreArticle で品質・量を評価
    → 不足なら追加ソースで再取得（Multi-Query）
    → n 段階まで繰り返す

        ↓

[4] 正規化
    タイトル・URL・本文・日時・ソース名を統一フォーマットに変換

        ↓

[5] 重複除去
    checkDuplicate でコサイン類似度による重複を検出・統合

        ↓

[6] 重要度スコアリング
    scoreArticle（LLM-as-judge）が各記事を評価
    （技術的重要度・新規性・関心領域との関連度）

        ↓

[7] 完全翻訳【並列実行】
    translateFull で英語記事を日本語に完全翻訳
    （技術用語は英語保持、原文構造維持、要約しない）

        ↓

[8] Markdown 出力
    writeMarkdown で重要度順に並べた md を生成

        ↓

[9] 音声ダイジェスト生成（generateAudio: true の場合）
    generateScript → generateAudio で音声ファイルを生成
    md 内に音声ファイルへのリンクを追記

        ↓

[10] 結果返却
     md テキスト + 音声ファイルパスを外側エージェントに返す
```

### MCP サーバーのインターフェース

```typescript
server.tool("fetch_ai_news", {
  query: z.string(),
  abstractionLayer: z.enum(["macro", "middle", "micro"]),
  targetSources: z.array(z.string()).optional(),
  date: z.string(),
  limit: z.number().min(3).max(20),
  userIntent: z.string(),
  generateAudio: z.boolean().default(false),
}, async (request) => {
  const agent = new NewsAgent(request);
  const result = await agent.run();
  return {
    content: [
      { type: "text", text: result.markdown },
      ...(result.audioPath
        ? [{ type: "text", text: `🎧 音声ダイジェスト: ${result.audioPath}` }]
        : []),
    ],
  };
});
```

## 13. 成功基準

- **Phase 1**: 1 コマンドでその日のダイジェスト md が生成できる。**完全翻訳の品質が満足レベル**。**10 記事で 3 分以内**。音声は簡易版のみ任意生成とする。
- **Phase 2**: 重複記事が目視で明らかに減り、重要度順が体感で正しい。量・質が不足した日もフォールバックで補完されている。テックブログからの収集が機能している。
- **Phase 3**: TUI 上で対話 → 情報ニーズ明確化 → ニュース収集 → md 生成が完結する。媒体・本数・トピックを柔軟に指示できる。
- **Phase 4**: 音声ダイジェストが、朝の準備中や散歩中に聞ける品質まで改善されている。
- **Phase 5**: 「X ブックマークを週 1 で見る」習慣が不要になる。
