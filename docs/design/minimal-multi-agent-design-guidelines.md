# 最小マルチエージェント設計ガイドライン

更新日: 2026-04-04

## 目的

- `ai-news-agent` の最小マルチエージェント構成を設計するときに、論点の切り方と判断軸を揃える
- 実装案に飛びつく前に、先に固定すべき設計上の境界を明確にする
- Issue `#11` の設計議論で、何を今決めるべきか、何を後回しにできるかを整理しやすくする

---

## 最重要の指針

### 1. まず「どの責務の議論か」を固定する

- 1回の議論では 1 つの責務だけを扱う
- `manager`、`source worker`、`judge`、`translation`、`shared memory` を同時に決めようとしない

なぜ重要か:

- マルチエージェント設計は、役割名だけ先に増えて責務境界が曖昧になりやすい
- 先に責務を分けないと、後で manager に何でも集まる

具体例:

- 良い例:
  - 「今決めたいのは、manager が持つ停止条件だけ」
- 悪い例:
  - 「manager が再探索して、worker が本文抽出して、judge が ranking して、そのまま翻訳も見て」

### 2. 役割名ではなく、入出力と判断権限で設計する

- `manager agent` という名前を決めても設計にはならない
- その agent が
  - 何を受け取るか
  - 何を判断してよいか
  - 何を返すか
  を定義する

なぜ重要か:

- マルチエージェントでは、役割名より契約のほうが重要
- ここが曖昧だと、後で framework を選んでも実装がぶれる

### 3. 「ユーザー価値」と「オーケストレーション都合」を分けて話す

- ユーザー価値:
  - 重要な一次情報を短時間で判断しやすくする
- オーケストレーション都合:
  - 並列実行しやすい
  - shared memory に載せやすい
  - 失敗を局所化しやすい

なぜ重要か:

- agent を増やす理由が、単なる実装の面白さになりやすい
- 増やす根拠は、ユーザー価値か品質特性に戻して説明できる必要がある

### 4. 今固定すべきものと、後で差し替えるものを分ける

今固定すべきもの:

- manager が持つ判断
- worker の責務境界
- shared memory の最小項目
- 停止条件 / 成功条件
- 一次情報優先ルール

後で差し替えてよいもの:

- 具体的な framework
- HTML 抽出ライブラリ
- translation model の細かい選定
- 並列数の最適値
- 音声の実装詳細

### 5. 最小マルチエージェントを守る

- 最初から agent を増やしすぎない
- `役割が違うから分ける` のであって、`なんとなく並列化したいから分ける` のではない

最低限の分割基準:

- 判断主体が違う
- 失敗時の扱いが違う
- 入出力の契約が違う
- 将来差し替えたい粒度が違う

### 6. 一次情報優先を architecture に埋め込む

- これは ranking の好みではなく、システムの設計原則
- Hacker News は補助ソースであり、公式情報の代替ではない
- Reddit や X を将来入れるとしても、主経路にはしない

なぜ重要か:

- どの agent が何を残すかのルールが曖昧だと、補助ソースが主役になりやすい

### 7. 部分成功を最初から設計する

- source worker の一部失敗
- 本文抽出失敗
- 翻訳失敗
- 一次情報不足

これらが起きても、全部を即失敗にするか、どこまで返すかを設計時点で決める

なぜ重要か:

- マルチエージェントは部分失敗が前提の構造になりやすい
- 失敗設計が後回しだと、最後に manager が曖昧な判断をするだけになる

## 設計議論で常に見るべき視点

### 1. 目的

- この agent / module は何のために存在するか
- なくても成立するなら、本当に必要か

### 2. 境界

- どこまでがこの責務か
- どこから先は別責務か

### 3. 契約

- 入力は何か
- 出力は何か
- 不変条件は何か

### 4. 停止

- いつ探索を止めるか
- いつ「十分な結果」とみなすか
- 再探索は何回までか

### 5. 品質

- 一次情報を残せているか
- 要約化せず翻訳できるか
- ノイズを落とせるか

### 6. 性能

- 5記事2分 / 10記事3分 を壊さないか
- 並列化で速くなるか、逆に遅くなるか

### 7. 失敗時

- どの失敗が全体失敗か
- どの失敗は部分成功にできるか
- ユーザーにどう返すか

### 8. 変更コスト

- 後で source を増やすとき、どこが壊れるか
- translation QA を足すとき、既存設計に無理がないか

## 最小マルチエージェント設計で特に見るべき観点

### 1. manager を太らせすぎていないか

- manager は全知全能ではない
- manager の責務は
  - 計画
  - 進行管理
  - 停止判定
  - 最終確定
  に寄せる
- 本文抽出や翻訳処理の中身まで持たせない

### 2. worker の責務が source adapter と混ざっていないか

- source adapter は取得
- worker は取得結果の解釈と shared memory への登録
- normalization / content extraction をどこでやるかを明示する

### 3. judge が ranking だけでなく選別ルールを持っているか

- `高 / 中 / 低` を付けるだけでは弱い
- 重複除去
- 一次情報優先
- 補助ソースの扱い
を定義する

### 4. translation を別責務として独立できているか

- 翻訳は ranking や source collection に埋め込まない
- 後で translation QA を追加しやすい境界にする

### 5. shared memory が会話ログ化していないか

- shared memory は長文の置き場ではない
- manager が次の判断をするための構造化情報に寄せる

推奨項目例:

- `id`
- `title`
- `url`
- `sourceType`
- `sourceName`
- `publishedAt`
- `isPrimarySource`
- `topicTags`
- `shortSummary`
- `relevanceScore`
- `status`
- `failureReason`

### 6. 成功条件が「記事数」だけになっていないか

- 記事数は必要だが十分ではない
- 最低限:
  - 必要件数
  - 一次情報の存在
  - Markdown 生成可能
  を満たす必要がある

## 議論のときに毎回使う質問

1. 今決めたい論点は何か
2. それは今決めないと何が壊れるか
3. 最低 2 つの選択肢は何か
4. その選択肢の違いは `責務 / 契約 / 性能 / 失敗時` のどこに出るか
5. この決定で固定される範囲はどこか
6. 後で差し替え可能な範囲はどこか
7. manager に寄せすぎていないか
8. shared memory に必要以上の情報を持たせていないか
9. 一次情報優先の原則が崩れていないか
10. 5記事2分 / 10記事3分 を壊さないか
11. 部分成功の扱いは説明できるか
12. 今回の決定は Issue `#11` のどの成果物に対応するか

## よくあるミス

### 1. agent 名を増やしただけで設計した気になる

- 名前ではなく責務と契約を決める

### 2. framework 前提で設計を始める

- `LangGraph ならこう書ける` から入らない
- 先に必要な責務と状態を決める

### 3. manager に何でも集める

- 再探索、ranking、翻訳条件、出力整形、失敗処理を全部 manager に持たせない

### 4. 共有メモリに本文を全部載せる

- コンテキスト肥大化と責務混線の原因になる

### 5. 一次情報優先を ranking の後工程に押し込む

- これは設計原則なので、judge と停止条件に最初から入れる

### 6. 再探索を無制限に許す

- 最小構成では 1 ラウンド程度に制限する

### 7. 失敗時を最後に考える

- 部分成功を返すかどうかは architecture の一部

## このガイドの使い方

### 1. 設計議論の前

- 今回の論点を 1 つだけ選ぶ
- その論点が `責務 / 契約 / 停止 / 性能 / 失敗時` のどれに近いか確認する

### 2. 設計議論の途中

- 2案以上を比較する
- manager に寄りすぎていないか確認する
- 後で差し替え可能な点を明示する

### 3. 設計議論の後

- 決定事項
- 採らなかった選択肢
- 理由
- 未決事項
を Issue `#11` または関連ドキュメントに残す

## まず最初に議論する順番

1. manager の責務
2. source worker の責務
3. shared memory の最小項目
4. normalization / content extraction の責務境界
5. manager の停止条件 / 成功条件
6. judge / dedupe の選別ルール
7. translation の責務
8. 標準フロー
9. エラー時の扱い
10. 性能と追加探索

この順番で進めると、最小マルチエージェント構成の骨格を先に固めてから、処理の流れと例外に進める。
